# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

GameVault is a Windows desktop game launcher (C#/WPF, .NET 10, win-x64 self-contained) for manually added games: it tracks playtime, auto-discovers save locations, keeps dated local backups and session notes, and handles screenshots/recordings. No cloud sync. The repository is public (source-available, all rights reserved: see `LICENSE`); the owner approves/merges PRs and owns release publication. A private archive of the earlier history exists; only this repository is used for work.

## Commands

The SDK is pinned by `global.json` (10.0.404, latestPatch roll-forward). A .NET *runtime* alone cannot build this repo; the matching SDK must be on `PATH`. Repository scripts need PowerShell 7 (`pwsh`).

```powershell
dotnet --version
dotnet restore GameVault.slnx --locked-mode             # do not let this rewrite packages.lock.json
dotnet build GameVault.slnx -c Release --no-restore     # warnings are errors: this is the lint gate
dotnet test GameVault.slnx -c Release --no-build --no-restore

dotnet test tests/GameVault.Tests --filter "FullyQualifiedName~StoreLaunch"      # focused
dotnet test tests/GameVault.App.Tests --filter "FullyQualifiedName~Notes"

pwsh -NoProfile -File ./scripts/verify.ps1              # the real acceptance gate
```

`verify.ps1` does a locked restore, Release build, full tests (plus two workflow-evidence JSON files), a fresh self-contained publish to `artifacts/publish-<guid>`, a runtime-file check, and a check that the output contains no `Data`/`Profiles`. A stale `artifacts/verification.json` is not evidence; re-run. Run one build/test/publish at a time. Installer/release scripts (`test-installer`, `test-capture-packaging`, `test-release`, `audit-release-source`, `build-installer`, `package-release`, `create-draft-release`, `smoke-draft-release`) are only for release work and need the owner's direction. CI (`.github/workflows/build.yml`, GitHub Actions on `windows-latest`) is deliberately quick before merging (owner's choice): a pull request to `main` runs one `verify` job (commit-address audit, `verify.ps1`, source-history audit). The long checks (installer boundary and silent install/upgrade/uninstall tests, capture-encode probe, performance harness) and the `private-draft-assets` release bundle run only when a release is prepared, by dispatching the workflow on `main` with no input (`gh workflow run build.yml --ref main`); do not move them back to pull requests without the owner. Pushes do not run CI. The app version lives only in `Directory.Build.props` (`GameVaultVersion`, plus `GameVaultPreview`: set it to the preview number being released, because the update check (and the automatic update, which downloads the release installer in the background, verifies it and runs it in place when GameVault is closed, keeping the player's data) compares `<version>-preview.<N>` with GitHub release tags, see `docs/update-check.md`; before an installer starts a verified safety copy and a fingerprint of `Data`/`Profiles` are made and the new version compares the library with it before opening it, `UpdateSafety`/`LibraryFingerprint`); Dependabot (weekly, grouped) PRs need their lock files regenerated by hand (`docs/development.md`). Check results with `gh run list` / the PR checks page instead of polling in loops. A test that only fails on CI is probably timing-dependent: look for hard-coded short timeouts in the test before suspecting the app. Known: on slow runners the headless WPF tests (`tests/GameVault.App.Tests`) sometimes all stall with 20-30 s timeouts, and `WorkflowValidationTests` (complete play workflow) has failed once; if the same commit passes elsewhere, `gh run rerun <id> --failed`.

PDFsharp stays at 6.2.3: it is the last release checked to be MIT-licensed, and 6.5.0 is AGPL-3.0/commercial dual-licensed, which would conflict with this repository's source-available licence (not legal advice) (Dependabot ignores it; changing that is the owner's licence decision). **Never add a licence, dependency, package, service, API or tool that needs paying or is not free** (no paid or commercial-only licences or tiers, no subscriptions, no billing accounts; check the licence and pricing of every new or bumped dependency and report what you found). Dependencies use exact versions with committed `packages.lock.json`; change them only deliberately (`dotnet restore GameVault.slnx --force-evaluate`) and review the lock diff.

## Architecture

- `GameVault.Core`: plain models/contracts, no WPF.
- `GameVault.Infrastructure`: `Storage/` (versioned JSON repository `AppDataStore*`, `ProfileFolders`, `ManagedPaths`), `Library/`, `Launching/`, `Playtime/`, `Saves/` (discovery, backup, restore, destinations), `Notes/`, `Artwork/`, `Capture/` (`CaptureCoordinator`, `CaptureMediaStore`, `NvidiaApp`, `NvidiaCaptureImporter`), `ApplicationWorkspace` (exclusive `.gamevault.lock` handle).
- `GameVault.App`: WPF shell; `MainWindow` partials (`.Navigation`, `.Tray`, `.Capture`, `.Performance`, `.Shell` for title-bar history, command palette, toasts and the now-playing chip; its logic is in `GameVault.Core/ShellModels.cs`, see `docs/ui-shell.md`); same-window views (`NotesView`, `BackupsView`, `RestoreView`, `SaveSourcesView`, cover search, `GameEditor`). A type named `*Window` may be hosted inline: check its base type. Capture UI in `Capture/`.
- Game information (`GameVault.Core/MetadataModels.cs`, `GameVault.Infrastructure/Metadata/`, `docs/game-data-sources.md`): `IGameMetadataProvider` per source (Steam store, Epic store page, GOG, Wikidata, HowLongToBeat, local file/launcher info), `MetadataResolver` (per-field provider order, first valid value wins, failures skipped, partial results reported), `GameMetadataService` (builds the request, identity, "Not the right game?" picker, saves per-game `metadata.json`), `AutoLookupQueue` (lookups for new games jump the queue; nothing is dropped while another lookup runs). New providers go through `PoliteHttp` (timeout, size cap, gap, no cookies/redirects, fixed HTTPS hosts; only a title or an id is ever sent). No accounts or API keys; IGDB/RAWG/SteamGridDB and PCGamingWiki data (CC BY-NC-SA) are deliberately not used. Values the owner typed or chose (description, cover, picked match) are never replaced by a lookup.
- Other feature areas: play actions and before/after hooks (`LaunchSettings` in `launch.json`, `ProcessHookRunner`), tags/categories and saved views (`TagRules`, `SavedViewList`, `library-tags.json`, `library-views.json`), Steam/Epic import (`StoreLibraryScanner`), whole-library backup/restore zip (`DataArchive`), diagnostics package and rolling log (`DiagnosticsPackage`, `AppLog`, `Logs/gamevault.log`), optional save-location database from the Ludusavi manifest (downloaded on request into `Cache/`, never bundled: `docs/save-location-database.md`). Window code is split into `MainWindow.*.cs` partials per feature (`.Metadata`, `.AutoInfo`, `.AboutDetails`, `.Tags`, `.PlayActions`, `.StoreImport`, `.DataBackup`, `.Diagnostics`, `.Overview`, `.Overhaul`); source-contract tests in `MainWindowStartupTests` check the XAML names and key wiring.
- Newer feature areas (preview 3 to 5), each with its logic in Core or Infrastructure and tests:
  - Start-up (`App.OnStartup`, order matters): a second start only wakes the running copy (`SingleInstance`), then a waiting update, the after-update library check, the always-shown startup window, the workspace lock, the capture-folder rename, then the main window.
  - Updates (`Infrastructure/Updates/`): background download and in-place install; `UpdateSafety` makes a verified data copy and a `LibraryFingerprint` before the installer starts.
  - Saves: `SaveCandidateRules` holds the known save locations (including the Rockstar titles, whose save files have no extension). Add a location as a candidate with a test on synthetic folders, and confirm it against a real installation before calling it fixed. Stored discovery documents accept only the payload kinds `any`, `bin`, `save`.
  - Game page (`MainWindow.Metadata`, `.AboutDetails`, `GameOverviewRules`): only the essentials show by default; everything else sits in `QuietExpander` sections that remember their state per run.
  - Settings (`MainWindow.Settings`, `Core/SettingsCatalog`): category pages with a search. A new option goes on a `Cat<Key>` page **and** into `SettingsCatalog.Entries` with the control's name; a test checks both. Rows show only the name and control: the explanation is `local:SettingHelp.Text` on the row (one or two short sentences, shown on hover and keyboard focus), its words go into the entry's keywords, and only what is sent over the network or replaced stays written on the page.
  - Rating (`StarRating`, `StarRatingControl`), capture gallery (`CaptureGallery`, `CaptureTile`, `ShellMedia` for Windows thumbnails, `MediaFolders`), online cover search filtering (`Artwork/WebCoverResults`: reads Google's result page, degrades to the plain page), profile import from another folder (`ProfileImporter`: add-only, never writes to the source), removing a cover (`cover-removed.marker` stops automatic lookups until Refresh info).
  - Steam hours (`SteamHours`, `SteamLocalData`, `SteamHoursService`, `MainWindow.SteamHours`): read-only from Steam's `localconfig.vdf`; link guards are described in `docs/game-data-sources.md`. The total is GameVault plus Steam time (the owner's choice, even where Steam also counted a session). Never print Steam account identifiers.
  - Statistics (`PlayStatistics`, `StatisticsService`, `StatisticsView`): computed from recorded sessions and corrections, never journals; undated time (adjustments, Steam hours) counts in all time only; charts are plain WPF, no chart library. Completion dates (`completion.json`) are written by the profile save when a game becomes Completed; earlier completions have no date and must not be invented.
  - Obsidian (`ObsidianVault`, `ObsidianApp`, `NoteExportWindow`, `MainWindow.Obsidian`): plain Markdown into a linked vault, by default `Obsidian Vault` inside the app folder (the owner's choice; part of the data backup). Notes are recognised by ids in their properties; one edited outside GameVault is never overwritten without asking, and nothing in a vault is deleted.
  - Motion (`MotionRules`, `Motion`): every transition goes through `Motion` (mark an element `local:Motion.Appear`), so Reduce motion and the Windows animation setting turn all of it off; 120 to 250 ms, nothing delays input, nothing animates while idle.
  - Statuses (`PlayStatuses`, `status.json`): `profile.json` stores only the original four; Backlog, Abandoned and Retired are a detail beside it, forgotten when the stored status changes. Use `PlayStatuses.From` to show a status. New data prepared for a later Backloggd import carries a source and external id (issues #94 to #98).
  - Playthroughs, journal and lists (`playthroughs.json`, `journal.json` per game; `Data/lists.json`): each record may carry `Source`/`ExternalId`, and saving the same import identity replaces it. Journal entries never change playtime. `CsvExportService` guards cells against spreadsheet formulas and writes no paths.
  - Two library games can never share a program; a removed profile with that program may be restored or left beside a new one (`GameDraft.BesideRemoved`).
- `GameVault.Capture`: lazy native capture backend (ScreenRecorderLib 7.0.1). Missing prerequisites must degrade gracefully and never block startup.

### Persistence

The data root is always `AppContext.BaseDirectory` (never the working directory or a game folder). New data goes in its own small document or marker file where possible: adding a field to an existing document makes older versions treat it as unreadable.

```
GameVault.exe
Data/settings.json  Data/backup-destinations.json  Data/capture-preferences.json  Data/library-views.json  Data/library-tags.json  Data/metadata-settings.json
Obsidian Vault/ (only when the player creates one)
Cache/ (downloaded save-location manifest)  Logs/gamevault.log  Logs/running.marker (exists while the app runs; a leftover means the last run ended unexpectedly)
Profiles/<game name>/          (older GUID-named folders are renamed once at startup; the ID lives in profile.json and .gamevault-id)
  profile.json  statistics.json  launch.json?  save-discovery.json  capture-source.json?  metadata.json?  cover.png  hero.jpg|png?
  rating.json?  cover-removed.marker?  steam-link.json?  completion.json?  status.json?
  Sessions/  Corrections/  Notes/Sessions/  Notes/review.json  Media/<date and time>/ (hidden .session-id inside)  Backups/<dated-backup>/
```

Every document is `schemaVersion`-tagged and rejects unknown fields; an unrecognised version is read-only (no auto-migration). Writes: validate, temp file in the same folder, flush, atomic replace, keep `.bak`. A corrupt primary with a valid `.bak` surfaces as Recovered/read-only and is never auto-promoted. Managed paths reject symlinks/junctions. **Always resolve a game's folder with `ProfileFolders.Resolve(paths, id)`; never `Path.Combine(Profiles, guid)`.** Backup retention default: latest 20 unpinned plus all pinned; external destinations are `<root>/<stable-id>/Backups`.

### Launch and elevation

`MainWindow` runs at normal integrity; an administrator game is started by a one-shot elevated helper (`ElevationBroker`/`BrokerPipe`) that hands observation handles back. Steam/Epic games launch through the store protocol and are tracked via detached-process handoff; GameVault does not bypass authentication or DRM.

### Capture

Per game the recorder is Auto (NVIDIA App when installed), GameVault, or NVIDIA App (`capture-source.json`). GameVault's recorder is registered with global shortcuts (default Ctrl+Shift+F9/F10/F11) only while a game using it runs. NVIDIA App has no API for starting recordings or setting folders, so GameVault only detects it read-only and copies its `.mp4`/`.png` files from the game's recorded sessions into the profile (see `docs/nvidia-app-capture.md`). `RecordingWatchdog` flags a recording whose video frames stop while audio continues.

## Testing

xUnit throughout. `tests/GameVault.Tests` (real filesystem, process fixtures), `tests/GameVault.App.Tests` (headless WPF/contract tests; passing is not proof of real pixel/input behaviour), `tests/Fixtures/GameProcessFixture`, `tests/BrowserDependencyProbe`, `tests/PerformanceHarness` (synthetic only).

Headless tests must never show a window or start a browser. To look at a changed layout before a person tries it, a temporary test can load the XAML fragment with `XamlReader` (strip event attributes, merge `Styles.xaml`, apply a theme) and save a `RenderTargetBitmap`; delete that test afterwards.

## Working conventions

- A person verifies UI, native dialogs, real games and installers. Do not launch the owner's apps, stores, games, browsers or installers to "test", and never kill a GameVault or game process. A green `verify.ps1` does not close the manual-acceptance issues (roadmap #1, screens #2, play-and-restore workflow #3, performance #4); the owner closes them.
- Commit identity: use the GitHub no-reply address for this repository (`git config user.email`), never a personal address (CI runs `scripts/audit-commit-emails.ps1` and fails a PR whose author, committer or co-author address is not a GitHub no-reply one; ask your person to turn on "Block command line pushes that expose my email" in their GitHub email settings). The history was rewritten once to remove a personal address; do not push any old branch or clone from before that, and never `git push --all` from an old checkout.
- Pull requests: one topic per PR, assigned to the person you work for. If a change touches the installer, packaging, capture encoding or performance-sensitive code, say so in the PR and offer to run the release checks early. A local green `verify.ps1` plus the source audit (`scripts/audit-release-source.ps1`) is the minimum before opening one; merge only when CI is green and the owner agrees.
- Issues and PRs: feature-sized work gets an issue first (assigned to the person you work for) and the PR links it (`Closes #N`, or `Refs #N` when more work remains); a PR may skip the issue only for a small bug or small change. Every issue gets labels: a type (`bug`, `enhancement`, `chore`, `refactor`, `documentation`, `testing`) and, where they fit, an area (`ux`, `performance`, `stability`, `security`, `accessibility`, `localization`, `themes`, `ci`, `dependencies`), plus `epic` for tracking issues and `manual-acceptance` when the owner must test by hand and close it. If nothing fits, create a new label with `gh label create <name> --description "..." --color <hex>` instead of leaving the issue unlabelled or mislabelled. After a PR is merged and its issue is closed, delete the PR's branch on GitHub (`gh pr merge --delete-branch`).
- Never commit real saves, profiles, credentials, installers or published binaries (`.gitignore` excludes `/Data/`, `/Profiles/`, `**/Backups/`, `artifacts/`, `work/`, `outputs/`). Never print or store tokens.
- GameVault is source-available, all rights reserved (see `LICENSE`; not an open-source licence) and installers are unsigned (signing was deliberately skipped); never infer release authorisation. The owner approves merges and owns releases, repository settings and collaborator changes.
- `licenses/windows-sdk/LICENSE.rtf` must stay byte-for-byte as shipped (`.gitattributes`).
- Releases: only the owner publishes. `scripts/create-draft-release.ps1` creates an **unpublished** draft from the verified CI bundle (it needs `GH_TOKEN` and, on this public repository, `GAMEVAULT_PUBLIC_REPOSITORY_APPROVED=true`); the draft smoke is a manual `workflow_dispatch` of `build.yml` with `draft_release_id`. The draft is built from the commit whose CI passed; see `docs/release-process.md`. Order for a preview release: merge a PR that sets `GameVaultPreview`, dispatch the release checks on `main` and wait for them to pass, download that run's `private-draft-assets`, create the draft with `-Tag v<version>-preview.<N>`, dispatch the smoke with the draft's id, then (only when the owner asked to publish) set the release notes (what is new, bugs fixed, how to update) and publish as a prerelease that is not "latest". The published app folder is trimmed (English-only framework resources, no `.pdb`): keep it that way.
- UI direction from the owner: show only what is needed by default and reveal the rest on demand; keep on-screen text short.
- Keep the same-window UI direction. Themes are plain data in `GameVault.Core/ThemeCatalog.cs` (add a theme by adding one entry; `ThemeTests` checks colour format and text contrast for every entry; the full-window picker with live previews is `ThemePickerView`); resolve routine implementation choices yourself and ask only when a decision is load-bearing.
- For a reported bug: record exact build/steps/expected/actual, find the failing boundary, add a meaningful regression, fix narrowly, run focused tests, then one full `verify.ps1` for the proposed revision.
- Start from `README.md`, `docs/development.md`, `docs/persistence.md`, `docs/store-game-launching.md`, `docs/portrait-cover-search.md`, `docs/nvidia-app-capture.md`; read other `docs/*` only as needed (some describe superseded milestones).

## Collaboration rules (two people, two Claudes)

- This file is shared: the owner's Claude and the collaborator's Claude both read it and both update it (through a PR, like any change). Keep it free of tokens, personal data and machine-specific paths; keep personal quirks in a git-ignored local file instead.
- Issue numbers restarted in this repository (the earlier private archive has the old numbers).
- Ownership: each person works on their own issues and PRs. Any issue a Claude creates is assigned to the person it is working for. A Claude may read the other person's issues and PRs but must not edit, comment on, retarget, close or merge them. If the other person's item needs action, tell your own person instead.
